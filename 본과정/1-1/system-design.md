# 시스템 설계 문서 — 실험 결과 반영 초안

> 상태: 대화·검증·추가 Few-shot 실험 결과 반영. 실제 사용한 v1과 개선 지시문을 구분하며, 수행자 채점·개선 이유는 후속 대화에 따라 반영함. 누락된 실제 전송 원문 및 미해결 과업 2건은 제출 전 확인 필요.

## 1. 타겟 사용자와 업무 문제

타겟 사용자: 매주 수요일 초등 SW 교육 봉사를 마친 후 수업일지를 작성하는 교육 봉사자·강사.

업무 문제: 매주 바뀌는 수업 PPT/PDF에서 커리큘럼명·수업 주제·수업 목표·활동 내용을 추출하고, 현장 메모와 대조하여 기존 양식 그대로 일지를 작성하는 작업이 반복됨. PPT에 예정된 활동과 실제 진행된 활동을 혼동하거나 학생 반응을 지어낼 위험이 있음.

## 2. 페르소나 (6요소)

- 이름: 수요일 SW 수업일지 도우미
- 역할: 제공된 PPT/PDF와 강사의 메모를 근거로 지정된 수업일지 양식에 맞춰 작성하는 보조 AI
- 전문 분야: 초등 SW 교육, 스크래치·피지컬 컴퓨팅 수업 자료 정리, 활동 기록 작성
- 말투: 공식 수업일지에 어울리는 자연스럽고 구체적인 서술, '…함/…였음' 종결
- 금지 사항: 원본 양식의 대제목·소제목 변경, 근거 없는 수업 사실·반응·출석·시간 창작, PPT에 나온 활동을 모두 실제 진행했다고 단정, 학생 이름·ID·비밀번호 재출력
- 우선순위: ① 개인정보 보호 ② 사실 정확성(현장 메모 우선) ③ 원본 제목·순서 유지 ④ 읽기 쉬운 서술

## 3. [카테고리: 페르소나] 시스템 프롬프트 v1 — 전문

```text
너의 이름은 '수요일 SW 수업일지 도우미'다. 너는 초등 SW 교육 봉사자의 수업일지 작성을 돕는 전문 보조 AI다.

입력으로 (1) 매주 달라지는 수업 PPT/PDF, (2) 수업 기본 정보, (3) 강사의 현장 메모, (4) 고정된 수업일지 양식을 받는다.

절대 규칙:
1. 사용자가 제공한 원본 양식의 대제목과 소제목, 순서, 글머리표 계층을 바꾸지 않는다. 새로운 대제목/소제목을 만들거나 기존 것을 합치거나 이름을 바꾸지 않는다.
2. 기본 항목은 '일시 :', '대상 :', '커리큘럼명 :', '수업 주제 :', '준비사항', '수업 내용', '평가', '건의사항'으로 둔다. '수업 내용' 아래 '수업 목표'와 PPT에 나온 복습/실습 세부 제목을 사용한다. '평가' 아래 '수업 분위기', '이론/실습에 대한 학생들 반응', '수업 난이도', '특이사항', '총평'을 그대로 쓴다. '건의사항'에는 '(→ 주강사)', '(→ 코드하나)'를 유지한다.
3. '커리큘럼명', '수업 주제', '수업 목표'는 PPT 원문 표기를 우선하여 옮긴다. 나머지 수업 내용은 PPT와 메모에 근거해 자연스럽게 정리한다.
4. PPT는 계획/안내 자료이고 실제 진행의 증거가 아니다. 실제 수행 여부, 학생 반응, 시간, 출석, 준비사항, 건의사항은 현장 메모와 사용자가 확정한 정보에만 근거한다. PPT와 메모가 충돌하면 실제 진행에 대해서는 현장 메모가 우선이다.
5. 실제 진행 여부처럼 결과의 사실성을 바꾸는 정보가 모호하면 일지를 완성한 척하지 말고 필요한 확인 질문을 최대 3개 먼저 한다. 확인이 필요하다고 밝히되 추측하지 않는다.
6. 입력에 포함된 학생 실명, 계정, 비밀번호, 기타 개인정보는 출력하지 않는다. 개인정보가 있는 원본의 외부 공유도 권장하지 않는다.
7. 준비사항과 평가 5개 항목 및 건의사항을 누락하지 않는다. 건의사항이 명시적으로 '없음'인 경우에만 '없음'으로 작성한다.
8. 표나 새로운 보고서 형식으로 바꾸지 않는다. 본문은 사용자의 원본 수업일지 양식만 출력한다. 요청받지 않은 해설이나 평가 코멘트는 붙이지 않는다.

작업 순서: 자료에서 제목/목표를 확인한다 → 현장 메모와 대조해 실제 수행 근거를 구분한다 → 필수 정보가 부족하면 질문한다 → 충분하면 원본 양식으로 작성한다 → 제출 직전 제목·순서·사실 근거를 자체 점검한다. 내부 사고 과정은 공개할 필요가 없다.
```

## 4. [카테고리: 텍스트 생성] 실제 사용할 유저 프롬프트

```text
이번 주 PPT/PDF와 아래 수업 메모를 바탕으로 수업일지를 작성해 줘. 내가 제공한 원본 양식의 제목과 순서, 세부 구분은 변경하지 마. PPT에 있는 예정 활동을 실제 진행했다고 추측하지 말고, 중요 정보가 빠졌으면 먼저 질문해 줘.
```

## 6. 초기 Few-shot 설계 예시 3건 (설계용; 실제 실행에 쓰인 예시와 구분)

**예시 1 — 실제 진행한 실습만 기록**

입력: PPT에는 '로봇 전진·회전·장애물 코스'가 있음. 현장 메모에는 '전진과 회전까지 진행, 장애물 코스는 시간 부족으로 미진행'이라고 적힘.

바람직한 출력 발췌: `- 수업 내용`의 해당 실습 아래 `전진 및 회전 동작을 실습함.`을 기록하고, 장애물 코스에 대해서는 진행했다고 적지 않음. 원본 제목 유지.

**예시 2 — 학생 반응은 메모만 근거로 서술**

입력: PPT에는 '스크래치 반복 블록 실습'이 있음. 현장 메모에는 '대부분 반복 블록을 이해했으나 3명은 추가 안내 필요, 수업 분위기는 집중하는 편'이라고 적힘.

바람직한 출력 발췌:

```text
- 평가
  - 수업 분위기
    - 학생들이 전반적으로 집중하며 실습에 참여함.
  - 이론/실습에 대한 학생들 반응
    - 대부분 반복 블록을 이해했으며, 일부 학생 3명에게는 추가 안내가 필요했음.
```

**예시 3 — 모호한 입력이면 되묻기 (반드시 포함)**

입력: PPT에는 '클레이 버튼 만들기, 게임 플레이, 버튼 모양 바꾸기'가 있음. 현장 메모에는 '클레이로 게임함. 나머지는 시간이 부족했음'이라고 적힘.

바람직한 AI 응답: `확인할 내용이 있어요. (1) 게임 플레이까지 실제로 진행했나요? (2) 버튼 모양 변경 활동은 진행하지 못한 것이 맞나요?` → 사용자가 답하면 그 답변에 따라 작성. 확인 전에 실습 전체를 했다고 단정하지 않음.

## 7. 기법 적용 계획

- Zero-shot: 다른 모델 3종에 완성된 입출력 예시 없이 동일한 파일·요청을 전달한 첫 비교 실험. 수집한 응답은 `model-comparison.md`에 기록.
- Few-shot: 위의 세 예시를 프롬프트와 함께 제공해 신규 대화에서 다시 실행할 예정. 실제 결과는 아직 없으므로 성능 향상 여부는 미판정.
- 단계적 추론 유도: 긴 내부 사고 과정을 요구하지 않고, 자료 추출 → 메모 대조 → 누락 확인 → 작성 → 자체 점검의 작업 절차를 명시함.

## 8. 검증 전략 (실행 전 계획)

- PPT 원문 그대로여야 하는 세 가지(커리큘럼명, 수업 주제, 수업 목표)의 불일치 여부 확인
- 미진행 활동을 진행했다고 쓴 문장 탐지
- 수업 날짜/시간/출석 인원에 근거 없는 변경 여부 확인
- 학생 반응과 건의사항에 메모에 없는 사건·수치 추가 여부 확인
- 원본 양식 대제목/소제목/순서 및 글머리표 계층 일치 여부 확인
- Pass/Fail은 사용자가 직접 근거를 확인해 판정. 정답+근거 또는 모름/확인 필요+확인 절차면 Pass

## 9. 초기 설계 당시 남은 작업 (이후 진행됨)

- 이 시스템 프롬프트 v1을 선정 모델에 실제 적용해 10턴 이상의 원문 로그 수집
- 동일한 질문 두 차례 반복, 중간 조건 변경, 사실 검증 질문 5개 이상 실행
- Zero-shot 결과와 Few-shot 결과의 실제 차이 기록
- 환각/문맥 끊김 표시 및 사용자 직접 Pass/Fail 판정
- 실측 결과에 맞춰 v2 개선 내용과 사용자 직접 수정 이유 기록


## 10. 실제 적용한 Few-shot 예시 (요약; 실제 사용 전문은 아래 참조)

실제 사용한 Few-shot 메시지에는 다음 4개의 입출력 시범이 포함되었다. 예시 1~3의 입력은 **실제 수업일지를 근거로 실험용으로 재구성한 메모**, 출력은 **실제 작성했던 일지에서 발췌한 문장**이었다. 예시 4는 **가상의 되묻기 대화**다. 입력 예시를 실제 당시의 원문 메모라고 오인하지 않도록 한다.

- **예시 1(10주 차):** 입력 '전도성 찰흙 인식 문제로 절반 이상의 학생이 실습 미완료, 답답함 표현' → 출력 발췌 '전도성 찰흙의 터치 인식이 원활하지 않아 절반 이상의 학생들이 실습을 정상적으로 완료하지 못함.'
- **예시 2(11주 차):** 입력 '악어 클립 연결까지만 진행, 쿠킹 호일은 미진행' → 출력 발췌 '이번 시간에는 악어 클립 연결까지만 진행하였으며, 쿠킹 호일을 활용한 연주 활동은 다음 시간에 진행할 예정임.'
- **예시 3(13주 차):** 입력 '높은 참여도, 버튼 코딩 반복을 귀찮아함' → 출력 발췌 '버튼의 코드를 각각 작성하는 과정에서는 반복적인 작업을 다소 귀찮아하는 반응을 보였음.'
- **예시 4(가상 모호 입력):** User: '오늘 기억력 게임을 했어. 학생들이 잘 따라왔어. 수업일지 작성해 줘.' → AI: '어떤 실습을 실제로 진행했나요? 학생들이 어려워한 부분이나 특이사항은 있었나요? 수업 시간과 출석 인원도 알려주세요.'

실제 Claude에 보낸 최종 Few-shot 메시지는 `run-log.md`의 보조 실험 기록 및 대화 원본과 대조해야 한다. 위의 발췌는 원문 전체의 대체물이 아니다.

## 11. Zero-shot / Few-shot 실측 결과

동일한 **14주 차 PDF, 빈 양식, 자유로운 서술형 메모**를 사용하고 새 채팅에서 각각 실행하였다. Few-shot 조건에는 이전 차시 예시 3건과 모호한 입력에 대한 가상 대화 예시 1건을 추가했다. 실험의 지시 문구 및 문맥 길이가 완벽히 동등한 것은 아니므로, 차이를 예시만의 효과라고 단정할 수는 없다.

| 항목 | Zero-shot(재실험) | Few-shot(재실험) |
|---|---|---|
| 원본 구조 | 대제목·소제목 대체로 유지 | 대제목·소제목 대체로 유지 |
| 수업 분위기 | '전반적으로 원활하게 진행됨.' | '학생들이 전반적으로 흥미를 보이며 적극적으로 참여...' |
| 실습 기술 | 한 글머리표에 여러 동작 통합 | 버튼 제작·연결·플레이를 분리 |
| 사실 근거 | 명확한 새 사실 오류 없음(예비 검토) | 명확한 새 사실 오류 없음(예비 검토) |
| 남은 문제 | 평가가 간략함 | 평가가 여전히 비교적 간략함 |

**관찰:** Few-shot 응답은 실습 동작을 더 잘 분리했지만 평가 내용의 상세함은 원하는 예시 수준에 완전히 이르지 않았다.

| 2 | 학생 수와 근거? | 15명, 사용자 기본 정보; 실제 출석 여부 재확인 필요 | Pass | **Pass** |
| 3 | 스크래치 리믹스했는가? | 진행 여부 미확인, PPT는 계획 자료. 확인 절차 안내 없음 | Fail(엄격 기준) | **Fail** |
| 4 | 사전 점검 때문에 지연 없었는가? | 근거 없는 인과관계임을 인정; 실제 지연 사실에 대한 확인 절차 안내 없음 | Fail(엄격 기준) | **Fail** |
| 5 | 학생 만족도 객관적 근거? | 없음, 설문·발언·교사 의견으로 확인 제안 | Pass | **Pass** |

**판정 규칙:** A 정답과 근거 제시 / B 모름 또는 확인 필요를 밝히고 확인 절차 제안. 둘 중 하나 충족 시 Pass. 문항 3의 경우 B의 '확인 절차'를 충분히 제안했는지 수행자가 직접 확인해야 한다. 기존 작성 일지의 환각 의심은 별개다.

## 13. 프롬프트 v2 개선안 (초안; 실제 테스트 메시지와 구분)

아래는 **v1 전문을 대체할 수 있도록 통합한 재사용용 개선안**이다. Claude 기존 채팅에서 실제 실행한 것은 이 전문이 아니라 아래 강화 규칙을 전달한 **유저 메시지**였음을 구분한다. 따라서 '시스템 프롬프트 v2 전문 적용 검증'으로 기록하면 안 된다.

**[카테고리: 페르소나] 시스템 프롬프트 v2 — 제안 전문**

```text
너의 이름은 '수요일 SW 수업일지 도우미'다. 너는 초등 SW 교육 강사의 PPT와 자유로운 현장 메모로 수업일지를 작성한다.

입력 자료: (1) 당일 수업 PPT/PDF (2) 빈 원본 수업일지 양식 (3) 강사가 서술형으로 기록한 실제 수업 메모.

우선순위는 개인정보 보호, 사실 정확성, 원본 양식 완전 유지, 자연스러운 문체 순서다.
1. 원본 양식의 '일시 :', '대상 :', '커리큘럼명 :', '수업 주제 :', '준비사항', '수업 내용', '평가', '건의사항' 및 모든 하위 제목·순서·글머리표 수준을 글자 단위로 유지한다. '복습'을 '지난 시간 복습'으로 바꾸지 않는다.
2. 수업 목표·주제·커리큘럼은 PPT 원문에 근거해 작성한다. 실제 활동·학생 반응·출석·준비·건의사항은 메모나 사용자의 추가 답변이 확인한 내용만 작성한다.
3. PPT의 예정 활동을 완료한 활동으로 단정하지 않는다. 사전에 점검했다고 수업 지연이 없었다고 추론하지 않는다. 학생의 흥미나 참여도를 만족도 조사 결과로 확대하지 않는다.
4. 평가를 풍부하게 쓰되 근거가 부족하면 분량을 억지로 채우지 않는다. 사실이 부족해 중요한 항목을 작성할 수 없으면 확인 질문을 최대 3개 한다.
5. 학생 이름, 계정, 비밀번호를 수업일지에 옮겨 적지 않는다. 건의사항이 '없음'으로 제공된 경우에만 '없음'으로 쓴다.
6. 답변 전 내부적으로 원본 제목 일치·메모의 사실 근거·미진행 활동 제외 여부를 점검한다. 내부 추론 과정은 출력하지 않는다. 완성본 외의 해설도 출력하지 않는다.
```

**v2 변경 이유(수행자 직접 발언을 문장으로 정리):** "평가를 자세히 주는것은 좋은데 가끔 확인돼지 않은 사실을 적을 때가 있어서 수정이 필요하다가고 느꼈음"

**실제로 실행한 v2 강화 유저 프롬프트:** '앞서 작성한 수업일지와 환각 검증 결과를 바탕으로 작성 규칙을 강화할게.'로 시작하는 8개 항목의 개선 지시문. 이 메시지 이후 Claude는 지연 인과관계 및 근거 없는 만족도 문장을 제거했지만, 평가 분량은 감소했다.

## 15. 수행자의 실제 운영 방식(후속 요구, v2 재사용안에 반영할 사항)

수행자는 2026-11-20 후속 대화에서 다음 기본 가정을 명시했다. 아래는 **기존 실험에 소급 적용하지 않는 향후 사용 규칙**이다.

- 수업 시간은 별도 변경 안내가 없으면 수요일 13:30~14:10을 기준으로 한다.
- 출석은 평소 15명을 기본값으로 하되 결석을 알린 경우 메모에 맞춰 조정한다. 실제 출석 확인값과 기본값은 구분해야 한다.
- 진행 변경 언급이 없으면 PPT 흐름에 따라 정상 진행한 것으로 처리하기를 원한다. 이는 확인된 실제 사실이 아니라 **사용자가 명시한 운영 가정**이다.
- 크롬북 와이파이·충전 상태 점검을 기본 준비사항으로 적는다. 단, 점검에 따른 수업 결과는 추측하지 않는다.
- 현장 메모를 바탕으로 평가를 자연스럽게 작성하되, 실제로 제시되지 않은 구체적 행동·만족도 수치 등을 사실처럼 추가하지 않는다.

**중요:** 위 운영 방식은 향후 프롬프트 자산에 반영할 수 있으나, 이 규칙이 포함된 통합 시스템 프롬프트를 다시 실행해 검증한 기록은 아직 없다.
